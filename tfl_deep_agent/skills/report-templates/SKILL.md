# Report templates

The report is rendered by code (`tfl_deep_agent/reports/render.py`) from the fields you pass to
`submit_report`. The Markdown files next to this one are the templates (`string.Template`
placeholders such as `$verdict_block`); you do not fill them yourself. Call
`list_report_templates` to see the list, or `list_report_templates(name="full_proof")` to see one
template with its placeholders.

The report is a **solution document**: a reader must see from it why the answer holds and how it
was obtained, not only "доказано, вот ссылка". The layout follows the pipelines' reports
(`cfl_system/examples/live_outputs/task_w1bw2w3_ticket50_result.md`,
`docs/examples/reg_grammar_SaSb_lean_proved/result.md`):

1. title and «Условие» (the task as the human gave it), then «Уточнение» when a follow-up message led to a new IR review (code; the follow-up texts in order, never in place of the task);
2. «Ответ»: the verdict in words, the class, «Уверенность: N%» and the review line (code);
   a warning callout when the machine check is not complete (code);
3. «Решение»: the idea (`hypothesis`) and the method, the lemmas used, the construction, the key
   claims, the steps «Шаг k. title» with the claim and «*Обоснование:*»;
4. «Заключение» (`conclusion`);
5. the Lean section when there is one;
6. the appendix «Проверка» (code): one table of the tool calls, the basis of the answer, the gate
   notes, the IR and review lines, the run line and, collapsed, the full call log with models and
   costs.

Code puts a small mark after each step or claim whose cited results passed, e.g.
«(проверено: regex_to_dfa ✓)», and puts the construction objects of the cited results (the DFA
transition table, the grammar, the LL table) under «Конструкция».

## Which template

| template | when | what it prints |
|---|---|---|
| `full_proof` | the default; any task where the proof matters | task, answer, idea and method, lemmas, construction, key claims, every step with its justification, conclusion |
| `exam_solution` | a solution to hand in at the exam | task, answer, idea and method, the chosen word or construction, the steps as a numbered list, conclusion |
| `short_verdict` | the user asked only for the answer, or an eval run | task, answer, `summary` (one or two sentences), the construction, the steps as a short numbered list |
| `lean_appendix` | a Lean proof exists and the user wants it shown | `full_proof` plus the Lean section |

The Lean section is appended to **any** template when the report has a `lean` block or the run's
evidence contains a `lean_check` result; `lean_appendix` only makes `full_proof` the body.
A run that ends without an accepted report (budget exhausted, call limit, error) is rendered by
code from the evidence ledger with the internal `partial` template: «Ответ не установлен»,
trust `not_verified`.

## submit_report fields

Write every text field in Russian. Formulas go in `$...$` (inline) or `$$...$$` (display) LaTeX;
they are printed as written and rendered with KaTeX in the HTML.

- `verdict`: the answer in words ("regular", "not CFL", "LL(1)", "unknown").
- `answer`: `yes` / `no` / `inconclusive`, the direction of the verdict (give it whenever the
  verdict text is not a plain "X" / "not X").
- `language_class`: `reg` / `cfl` / `dcfl` / `ll`.
- `method`: the method in one line ("лемма о накачке для КС-языков", "ДКА по выражению и сверка с IR").
- `hypothesis`: the idea of the solution in two to four sentences: what you expect and why, and
  why this method gives it. It is printed as «Идея.» at the top of «Решение».
- `lemmas` (optional): `[{theorem_id, use}]`. `theorem_id` is a section id from `list_theorems`
  (`"2.0"`: CFL pumping and Ogden quantifiers; `"1.1"`: Yu's pumping lemma for DCFL; `"1.2"`:
  Shallit's theorem; `"3.3"`: how to prove "not LL(k) for any k"); code prints the section title,
  its status marker and the line range of docs/THEORY.md. `use` says how the lemma is applied in
  this solution. Do not restate the lemma from memory; an unknown id is rejected. Cite statements,
  not the repository checklists (`"I.4"`, `"II.4"`) or the live-run log (`"5"`).
- `construction`: the actual object the solution rests on, not a pointer to it:
  - a DFA as a Markdown table, one row per state: `| состояние | a | b | принимающее |`, the
    start state marked `→`;
  - a grammar in a ``` block, one nonterminal per line: `S → aS | B`;
  - an LL table, or the FIRST/FOLLOW sets of the alternatives;
  - for a pumping argument, the chosen word with its parameters ($w = a^p b^p c^p$, $|w| \ge p$).
  One or two sentences may explain what the states or nonterminals mean.
- `claims` (optional): the key claims of the proof, `[{text, evidence_ids}]`
  ("a^(3i+2) b^i ∈ L for every i", "the DFA accepts exactly L").
- `steps`: the proof, `[{title, claim, justification, theorem_ids, evidence_ids}]`.
  - `title`: the short step name ("Описание языка", "Выбор слова", "Разбор случаев").
  - `claim`: one statement, the result of the step.
  - `justification`: the argument that proves the claim: the derivation, the case split, the
    counting, the induction. "Проверено инструментом", "см. результат" or a tool name alone is not
    a justification; say what the tool computed and why that gives the claim.
  - `theorem_ids`: the THEORY.md sections the step uses; `evidence_ids`: the tool calls that check
    it.
- `conclusion`: the closing paragraph: what the steps give together and the answer. If you leave
  it empty, `summary` is printed instead.
- `summary`: two or three sentences: hypothesis, method, conclusion (the body of `short_verdict`).
- `evidence_ids`: the tool-call ids supporting the verdict as a whole.
- `ir_fingerprint`: the fingerprint of the IR the oracle results refer to (from `validate_ir`).
- `template`: one of the four names above.
- `lean` (optional): `{evidence_ids, proof_path, note}`: the ids of the `lean_check` calls, the path
  of the proof file, a short note. The Lean status and axioms are read from those ledger entries,
  not from your text.

## Evidence ids

- Every claim and step lists the ids of the tool calls whose results support it. An id is the
  exact `tool_call_id` of the call in this run (the id shown in the evidence ledger, e.g.
  `toolu_01XbRK8X...`). Never cite a tool name (`regex_to_dfa`) or an id you made up: an id that
  is not in the ledger is listed in «Проверка», the claim gets trust `not_verified`, and at verdict
  level it lowers the trust one level.
- A step with no id is listed in «Проверка» as resting on your words alone.
- Never write "проверено", "verified", a confidence number or a trust level in the text: code
  computes them (docs/VERDICT_POLICY.md) and a sentence like that is only your claim.
- Do not paste tool JSON. Do not write a section named «Проверка» or an answer box: code
  adds them to every report.
- Lines of your text that start with `#` or `>` are escaped, so they cannot open a new section or
  a callout. A ``` block is allowed only in `construction`; elsewhere its fence is escaped.

## Human review

At HITL 2 the human sees the rendered draft and approves it, edits fields (the edited fields are
listed in the report) or returns it with a comment. A run with `--auto-approve` is marked
"без проверки человеком".
