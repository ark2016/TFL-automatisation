# Report templates

The report is rendered by code (`tfl_deep_agent/reports/render.py`) from the fields you pass to
`submit_report`. The Markdown files next to this one are the templates (`string.Template`
placeholders such as `$verdict_block`); you do not fill them yourself. Call
`list_report_templates` to see the list, or `list_report_templates(name="full_proof")` to see one
template with its placeholders.

The structure follows the golden reports `docs/examples/reg_grammar_SaSb_lean_proved/result.md` and
`docs/examples/cfl_ticket50_w1bw2w3_lean_proved/result.md`: task, verdict, method, hypothesis,
lemmas used, the proof as numbered steps, conclusion, Lean block.

## Which template

| template | when | what it prints |
|---|---|---|
| `full_proof` | the default; any task where the proof matters | task, verdict, method, hypothesis, lemmas, key claims, every step with its justification, conclusion |
| `exam_solution` | a solution to hand in at the exam | task, answer, the chosen word or construction (`construction`), the steps as a short numbered list, conclusion |
| `short_verdict` | the user asked only for the answer, or an eval run | task, verdict, `summary` (one or two sentences) |
| `lean_appendix` | a Lean proof exists and the user wants it shown | `full_proof` plus the Lean section |

The Lean section is appended to **any** template when the report has a `lean` block or the run's
evidence contains a `lean_check` result; `lean_appendix` only makes `full_proof` the body.
A run that ends without an accepted report (budget exhausted, call limit, error) is rendered by
code from the evidence ledger with the internal `partial` template: verdict "не установлен",
trust `not_verified`.

## submit_report fields

- `verdict`: the answer in words ("regular", "not CFL", "LL(1)", "unknown").
- `answer`: `yes` / `no` / `inconclusive`, the direction of the verdict (give it whenever the
  verdict text is not a plain "X" / "not X").
- `language_class`: `reg` / `cfl` / `dcfl` / `ll`.
- `method`: the method in one line ("лемма о накачке для КС-языков", "ДКА по выражению и сверка с IR").
- `hypothesis` (optional): the hypothesis and why you chose the method.
- `lemmas` (optional): `[{theorem_id, use}]`. `theorem_id` is a section id from `list_theorems`
  (`"2.0"`: CFL pumping and Ogden quantifiers; `"1.1"`: Yu's pumping lemma for DCFL; `"1.2"`:
  Shallit's theorem; `"3.3"`: how to prove "not LL(k) for any k"); code prints the section title,
  its status marker and the line range of docs/THEORY.md. `use` says how the lemma is applied. Do
  not restate the lemma from memory; an unknown id is rejected. Cite statements, not the repository
  checklists (`"I.4"`, `"II.4"`) or the live-run log (`"5"`).
- `claims` (optional): the key claims of the proof, `[{text, evidence_ids}]`
  ("a^(3i+2) b^i ∈ L for every i", "the DFA accepts exactly L").
- `steps`: the proof, `[{title, claim, justification, theorem_ids, evidence_ids}]`. `title` is the
  short step name ("Предположение", "Выбор слова"); `claim` is the statement of the step;
  `justification` is the argument; `theorem_ids` are the THEORY.md sections the step uses.
- `construction` (optional, `exam_solution`): the word chosen for a pumping lemma, the grammar,
  the automaton, the LL table summary.
- `conclusion`: the closing paragraph. If you leave it empty, `summary` is printed instead.
- `summary`: two or three sentences: hypothesis, method, conclusion.
- `evidence_ids`: the tool-call ids supporting the verdict as a whole.
- `ir_fingerprint`: the fingerprint of the IR the oracle results refer to (from `validate_ir`).
- `template`: one of the four names above.
- `lean` (optional): `{evidence_ids, proof_path, note}`: the ids of the `lean_check` calls, the path
  of the proof file, a short note. The Lean status and axioms are read from those ledger entries,
  not from your text.

## Evidence ids

- Every claim and step lists the ids of the tool calls whose results support it. An id is the
  `tool_call_id` of the call (the id shown in the evidence ledger).
- A claim with no id is printed with the mark "держится только на словах модели". An id that is
  not in the ledger is printed as such, and the claim gets trust `not_verified`; at verdict level
  it lowers the trust one level.
- Never write "проверено", "verified", a confidence number or a trust level in the text: code
  computes them (docs/VERDICT_POLICY.md) and a sentence like that is only your claim.
- Do not paste tool JSON. Do not write a section named "Свидетельства, модели и расходы": code
  appends it to every report.
- Lines of your text that start with `#`, `>` or three backticks are escaped, so they cannot open
  a new section, a callout or a code block of the report.

## Human review

At HITL 2 the human sees the rendered draft and approves it, edits fields (the edited fields are
listed in the report) or returns it with a comment. A run with `--auto-approve` is marked
"без проверки человеком".
