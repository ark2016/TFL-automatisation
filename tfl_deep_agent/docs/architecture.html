TFL Deep Agent

Отдельный подход к задачам ТФЯ на deepagents, рядом с существующими пайплайнами. Агент принимает задание текстом, PDF или картинкой и сам строит план. Он выбирает инструменты и модели, запускает субагентов и параллельные workflow в пределах бюджета из настроек и готовит отчёт по шаблону, который утверждает человек.

папка tfl_deep_agent/ ветка feat/deep-agent deepagents 0.7.34 langchain 1.4.x UI вкладка в TFL Lab старые пайплайны не трогаем

Принятые решения

Охват
Один агент на все классы

REG, CFL, DCFL и LL(k) различаются skill-файлами и набором инструментов. Старые пайплайны агенту как инструмент не даём: это отдельный подход, и его нужно сравнивать с ними честно.

Вход
Текст, PDF или картинка

Файл расшифровывает субагент intake с поддержкой изображений. IR агент строит сам, когда ему нужны оракулы.

Оркестрация
Агент сам выбирает субагентов и модели

Есть готовые роли, ad-hoc субагенты через spawn_subagent и параллельные workflow через run_workflow. Модель для каждого шага (Haiku, Sonnet или Opus) агент выбирает из списка, разрешённого в настройках.

Деньги
Лимиты в настройках

Лимиты на задачу, на день и на субагента, плюс резерв на отчёт. Перед каждым вызовом модели считается худший случай. Деньги кончились — агент сдаёт отчёт с тем, что успел.

Код агента
Локальный Docker

Контейнер без сети, с лимитами, код репозитория смонтирован только на чтение. Lean проверяется в уже собранном образе tfl-lean4.

Итог
HITL и отчёт по шаблону

Две остановки: после формализации и на отчёте. Шаблоны строятся по эталонам из docs/examples/*_lean_proved.

Журнал свидетельств как основа для HITL. Middleware записывает каждый вызов инструмента, агент этот журнал не редактирует. Каждая запись получает уровень доверия по docs/VERDICT_POLICY.md. Журнал ничего не решает за человека, он показывает, какие утверждения отчёта проверены машинно, а какие держатся только на словах модели.

Где здесь ReAct

Отдельно добавлять ReAct не нужно, он появляется сразу. create_deep_agent собирает агента через langchain.agents.create_agent: модель возвращает tool_calls, их исполняет ToolNode, результат возвращается модели как наблюдение, и так до финального ответа. Это обычный LangGraph-граф, поэтому работают стриминг, checkpointer и interrupt.

Сейчас порядок действий жёстко задаёт граф пайплайна, здесь его выбирает модель. Инварианты, которые раньше держал граф, переходят в четыре места:

  • skills: методички по классам языков, типовые ловушки, применимые теоремы;
  • middleware: бюджет, журнал свидетельств, лимиты вызовов, прерывания для HITL;
  • политика оркестрации: разрешённые модели, глубина вложенности субагентов, параллелизм;
  • финальный рендер: блок свидетельств и уровни доверия в отчёт вставляет код, а не модель.

Вход: текст, PDF, картинка

  1. Приём файла. Текст передаётся как есть. PDF и изображения (PNG, JPG, WebP) уходят в API Anthropic как content-блоки document и image в base64, Claude читает их напрямую. Ограничения на размер и число страниц задаются в настройках.
  2. Расшифровка. Субагент intake (по умолчанию Sonnet) переписывает условие в нормализованный текст с Unicode-формулами вида {aⁿbⁿ | n ≥ 0}. Если в PDF несколько задач, он возвращает их список, и человек выбирает нужную. Неуверенно прочитанные места помечает отдельно, например «индекс у w: 1 или l?».
  3. HITL 1. Человек видит рядом исходник (страницу или картинку), расшифровку, пересказ IR от ir-builder и примеры слов из языка и не из языка. Расшифровку и IR можно поправить до того, как на них начнутся доказательства.

Главному агенту дальше передаётся утверждённый текст и IR, а исходный файл остаётся доступен по пути /input. Так в контексте каждого шага не лежат тяжёлые страницы PDF, а стоимость расшифровки платится один раз.

Оговорка. Оракулы проверяют утверждения относительно IR, который построил агент. Если расшифровка или IR неверны, все проверки будут зелёными, но про другой язык. Поэтому HITL 1 включён по умолчанию, а отчёт явно пишет «проверено относительно IR №…».

Динамические субагенты и workflow

Готовых ролей хватает на типовой путь. Для нестандартных задач у агента есть два инструмента, которые он вызывает сам.

spawn_subagent: субагент под конкретную подзадачу

spawn_subagent(
  name="nerode-classes",
  instructions="Найди бесконечное семейство попарно различимых префиксов для IR №2 ...",
  model="sonnet",                 # haiku | sonnet | opus, только из allowed в настройках
  tools=["sample_words", "check_membership", "nerode_probe", "get_theorem"],
  budget_usd=0.40,                # вычитается из остатка родителя, больше остатка нельзя
  output_schema={...},            # необязательно: структурированный ответ
  reason="перебор префиксов, Opus не нужен"   # пишется в журнал
)

Под капотом это create_agent с выбранной моделью и подмножеством инструментов из whitelist. Инструменты оркестрации ad-hoc субагенту по умолчанию не выдаются, вложенность ограничена настройкой max_spawn_depth (по умолчанию 2).

run_workflow: параллельный план

run_workflow(steps=[
  {"id": "pump",   "role": "prover", "model": "sonnet", "task": "доказательство через лемму о накачке"},
  {"id": "ogden",  "role": "prover", "model": "sonnet", "task": "доказательство через лемму Огдена"},
  {"id": "parikh", "role": "prover", "model": "haiku",  "task": "проверить, решает ли Парикх"},
  {"id": "judge",  "role": "critic", "model": "opus", "depends_on": ["pump", "ogden", "parikh"],
   "task": "выбрать корректное из трёх и найти дыры"}
], budget_usd=2.0)

Спецификация компилируется в LangGraph StateGraph с fan-out через Send: тот же механизм, что в текущих пайплайнах, только граф строит агент. Перед запуском код проверяет, что граф ацикличен, модели разрешены, число параллельных веток не больше max_parallel, а оценка стоимости укладывается в бюджет. Если оценка не укладывается, агент получает отказ с цифрами и упрощает план.

Как агент выбирает модель

МодельПодсказка в системном промпте
Haiku 5.5Механика: перебор вариантов, проверка формата, массовые вызовы оракулов, черновые гипотезы.

Бюджет и настройки

Настройки лежат в tfl_deep_agent/settings.json. Файл в .gitignore, в репозитории только settings.example.json. CLI читает их сам, TFL Lab редактирует через модуль настроек пакета. Цифры ниже приведены для примера и правятся в UI.

{
  "budget": {
    "per_task_usd": 5.00,            // жёсткий потолок на одну задачу
    "per_day_usd": 20.00,            // сумма по всем задачам за сутки
    "per_subagent_max_usd": 2.00,    // один субагент или ветка workflow
    "reserve_for_report_usd": 0.30   // неприкосновенный остаток на отчёт
  },
  "models": {
    "allowed": ["claude-haiku-5-5", "claude-sonnet-5-5", "claude-opus-5-5"],
    "roles": {"main": "claude-opus-5-5", "intake": "claude-sonnet-5-5", "ir_builder": "claude-sonnet-5-5",
              "prover": "claude-opus-5-5", "critic": "claude-opus-5-5", "lean": "claude-opus-5-5",
              "coder": "claude-sonnet-5-5"},
    "opus_needs_reason": true
  },
  "limits": {"max_model_calls": 80, "max_tool_calls": 300, "max_parallel": 4, "max_spawn_depth": 2},
  "hitl":   {"formalization": true, "report": true, "execute": false},
  "intake": {"max_pdf_pages": 20, "max_file_mb": 10}
}

Как соблюдается лимит

  • Иерархия. Бюджет задачи делится между субагентами и ветками workflow. Потомку выделяется кусок из остатка родителя, и потратить больше выделенного он не может.
  • Проверка перед вызовом. BudgetMiddleware в wrap_model_call считает худший случай: входные токены плюс max_tokens по ценам из config.py. Если сумма больше остатка, вызов не делается, а агент получает сообщение с цифрами.
  • Учёт после вызова. Расход считается по фактическому usage ответа, с учётом кеша. Стоимость видна по каждой роли и каждой модели.
  • Сворачивание. Когда остаток доходит до reserve_for_report_usd, агент получает инструкцию сдать отчёт. Новые субагенты и workflow с этого момента запрещены. Если отчёт не сдан, рендер собирает частичный со статусом budget_exhausted.
  • Суточный лимит считается по журналу расходов в каталоге прогонов. Новую задачу нельзя запустить, если её per_task_usd не помещается в остаток дня.
  • Live-режим включается только флагом --live в CLI или подтверждением confirm_spend в UI, как сейчас у Formalize.

Для ориентира, эталонные прогоны пайплайнов на Opus из docs/examples: REG, грамматика SaSb, $0.89 и $2.11 на Lean; CFL, ticket 50, $2.39 и $1.59 на Lean. Агент с ReAct-циклом, скорее всего, будет дороже, поэтому по умолчанию заложено $5 на задачу.

Доверие, HITL и отчёты

Журнал свидетельств

  • EvidenceMiddleware через wrap_tool_call записывает каждый вызов, включая вызовы внутри субагентов и веток workflow, в run_dir/evidence.jsonl: id, инструмент, аргументы, результат, trust, модель, стоимость.
  • Уровень trust ставит обёртка инструмента по таблице из VERDICT_POLICY, модель на него не влияет.
  • В submit_report каждое утверждение ссылается на id записей. Несуществующий id делает утверждение not_verified.
  • Итоговый confidence ограничен потолком policy по сильнейшему подтверждающему свидетельству (переиспользуем agent_system/lib/result_verdict.py). Самооценка модели его не повышает.

Точки HITL

  1. Формализация (включена): расшифровка, IR и примеры слов, см. раздел «Вход».
  2. Отчёт (включена): submit_report прерывает граф. Можно утвердить, поправить поля (правка помечается в отчёте) или вернуть с текстом. После возврата агент продолжает работу с замечанием в контексте.
  3. execute (выключена): подтверждение каждого запуска кода, если нужно.

Состояние хранится в SQLite-checkpointer в run_dir. На точке HITL процесс агента завершается со статусом awaiting_human, а после решения человека запускается новый процесс с Command(resume=...). Держать процесс в ожидании не нужно, а прогон переживает перезапуск сервера. Флаг --auto-approve нужен для eval и тестов, в отчёте он фиксируется как «без проверки человеком».

Шаблоны отчётов

Шаблоны лежат в skill /skills/report-templates/: в SKILL.md описано, когда применять шаблон, рядом лежит Markdown с плейсхолдерами. Рендер без новых зависимостей, на string.Template. Структуру берём из эталонов docs/examples/reg_grammar_SaSb_lean_proved и cfl_ticket50_w1bw2w3_lean_proved: гипотеза, доказательство по шагам с леммами, заключение, Lean-блок.

short_verdictВердикт, одна-две строки обоснования, свидетельства.
lean_appendixДобавляется к любому шаблону, если есть Lean-доказательство: статус, аксиомы, ссылка на proof.lean.

Блок «Свидетельства, модели и расходы» в конце любого шаблона генерирует код, а не модель. В эталоне ticket 50 есть известная ошибка: неформальное доказательство цитирует неверный пример для p = 4. Этот случай станет регрессионным тестом для критика.

Docker-sandbox

docker run -d --name tfl-sbx-<run_id> \
  --network none --read-only --tmpfs /workspace:rw,size=256m \
  --memory 1g --cpus 1 --pids-limit 256 --user 1000:1000 \
  --security-opt no-new-privileges --cap-drop ALL \
  -v <repo>:/opt/tfl:ro  tfl-sandbox:latest  sleep infinity
# execute(cmd, timeout) → docker exec … (таймаут на каждый вызов, вывод обрезается до N КБ)
# в конце прогона: docker rm -f
  • Образ tfl-sandbox: python:3.12-slim и зависимости репозитория. Код репозитория смонтирован в /opt/tfl только на чтение, поэтому в sandbox можно импортировать CYK, DFA и остальные модули.
  • Lean не входит в этот образ, потому что он тяжёлый из-за Mathlib. Он остаётся в tfl-lean4, туда ходит только lean_check.
  • Пути Windows конвертируются функцией _windows_docker_path из type_check.py. Если Docker недоступен, execute не регистрируется, и отчёт это отмечает.

Открытые вопросы

По каждому указан вариант, который возьму, если не будет других указаний.

  1. Какой уровень доверия давать перебору в sandbox?Беру well_formed: произвольный код может проверять не то, что заявлено. bounded_pass оставляю только whitelisted-оракулам.
  2. Значения бюджета по умолчанию.Беру $5 на задачу, $20 в день, $2 на субагента, $0.30 резерва. Всё правится в настройках.
  3. Может ли агент выбирать Opus свободно?Да, если Opus в списке разрешённых, но с обязательной причиной в журнале (opus_needs_reason).
