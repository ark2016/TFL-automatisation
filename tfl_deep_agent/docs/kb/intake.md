# Вход задачи: текст, PDF, изображение

Как задача попадает в агента, какие у входа лимиты, как роль `intake` переписывает PDF или картинку в текст и как человек проверяет эту расшифровку. Связанные заметки: [[roles-and-subagents]], [[hitl-and-review-modes]], [[budget]], [[run-lifecycle]], [[tfl-lab]], [[testing-and-mock]].

Источники: `tfl_deep_agent/intake/files.py`, `tfl_deep_agent/prompts/intake.md`, `tfl_deep_agent/hitl.py`, а также `tfl_deep_agent/roles.py`, `tfl_deep_agent/settings.py`, `tfl_deep_agent/config.py`, `tfl_deep_agent/cli.py`, `ui_server/deep_routes.py`.

## Общая схема

1. Вход проходит валидацию в `intake/files.py` и превращается в `TaskInput` (или `IntakeError`).
2. Текстовая задача идёт в первое сообщение как есть. Для PDF и изображения в первое сообщение попадает только указание: файл лежит в `/input/task.<ext>`, читать его самому не нужно, переписать надо ролью `intake`, затем формализовать ролью `ir-builder`.
3. Роль `intake` читает файл и возвращает текст в двух разделах.
4. На HITL 1 человек видит эту расшифровку рядом с IR и может её исправить.

## Точки входа (`intake/files.py`)

| Функция | Кто вызывает |
|---|---|
| `from_text` | текстовая задача (CLI, TFL Lab поле `text`) |
| `from_path` | CLI `--file` |
| `from_bytes` | общая часть; сырые байты + подсказки `name` и `declared_mime` |
| `from_base64` | загрузка из TFL Lab (`file_b64`, допустим `data:`-URL) |

Все четыре возвращают `TaskInput` либо бросают `IntakeError`. У ошибки есть устойчивое поле `code`: `empty`, `too_large`, `too_many_pages`, `unsupported_type`, `type_mismatch`, `corrupt`, `encrypted`, `not_utf8`, `bad_base64`, `not_found`, `image_too_large`. CLI и сервер добавляют код в текст сообщения в скобках.

## Как определяется тип

> [!warning] Тип решает содержимое, а не расширение
> Тип определяется по сигнатуре (`sniff_mime`): `%PDF-`, сигнатура PNG, `FF D8 FF` для JPEG, `RIFF....WEBP` для WebP. Перед `%PDF-` допускаются пробельные символы и BOM.

- Расширение и `declared_mime` (тип от браузера) только подсказки. Несовпадение с содержимым не ошибка: файл обрабатывается по содержимому, а в `TaskInput.warnings` пишется предупреждение (типичный случай: `.jpg`, внутри которого PNG). В TFL Lab предупреждения показываются как «предупреждения intake».
- Расширение `.pdf` или картинки при неизвестной сигнатуре это ошибка `type_mismatch`: файл повреждён или не тот.
- Известные неподдерживаемые форматы (GIF, BMP, TIFF, ZIP/DOCX/ODT, DOC/XLS, RTF, исполняемые, HEIC/HEIF, AVIF) отклоняются с точным названием (`unsupported_type`).
- Файл без известной сигнатуры принимается как текст, только если нет NUL-байтов в первых 8192 байтах и он читается как UTF-8 (`utf-8-sig`). Иначе `unsupported_type` или `not_utf8`. Неизвестное расширение у такого текста даёт предупреждение.
- Текст нормализуется: переводы строк к `\n`, NFC, `strip()`. Именно NFC, а не NFKC: NFKC сложил бы верхние и нижние индексы (aⁿ в an). Пустой текст это `empty`.
- Расширения, которые принимает CLI: `.txt`, `.md` (текст) и `.pdf`, `.png`, `.jpg`, `.jpeg`, `.webp` (файлы). Остальные CLI отвергает до чтения файла (`cli.py`).

## Лимиты

Два лимита берутся из `settings.json`, раздел `intake` (по умолчанию в `settings.py` `DEFAULTS["intake"]`): `max_file_mb` = 10 и `max_pdf_pages` = 20. Класс `IntakeLimits` проверяет, что `max_file_mb > 0` и `max_pdf_pages >= 1`. 1 MB здесь это 1024 * 1024 байт.

Сверх этого действуют жёсткие пределы Anthropic API; настройки могут их только понизить:

| Что | Предел | Константа |
|---|---|---|
| Изображение, размер | 5 MB | `API_IMAGE_MAX_BYTES` |
| Изображение, сторона | 8000 px | `API_IMAGE_MAX_SIDE` |
| PDF, страниц | 100 | `API_PDF_MAX_PAGES` |
| PDF | не зашифрован | код `encrypted` |

Нюансы, которые легко пропустить:

- Лимит страниц это `min(max_pdf_pages, API_PDF_MAX_PAGES)`. Сообщение называет источник предела: настройка или лимит API.
- Страницы считает `pypdf` (`pdf_page_count`, `strict=False`). `pypdf` входит в extra `[deep]`; без него PDF-вход падает с `corrupt` и подсказкой установить extra.
- Размеры изображения читаются из заголовка собственным кодом (`image_size`), без Pillow. Не удалось прочитать заголовок: `corrupt`.
- Размер проверяется до чтения: `from_path` смотрит `stat().st_size`, `from_base64` оценивает по длине base64 до декодирования.
- Лимит применяется ко всем входам, включая текст (`from_text` проверяет размер UTF-8 байтов).
- Лимит тела HTTP-запроса в TFL Lab выводится из `intake.max_file_mb`: base64 (×4/3) плюс запас, но не больше потолка (`max_body_bytes` в `ui_server/deep_routes.py`). Фронтенд проверяет размер заранее, сервер проверяет повторно.

Поменять лимиты можно в `settings.json` (в TFL Lab есть поля «страниц PDF» и «размер файла, MB»). Поднять выше пределов API не получится: проверка API остаётся.

## `TaskInput`

Неизменяемая запись с полями `kind` (`text` / `pdf` / `image`), `mime_type`, `name`, `data`, `text`, `pages`, `width`, `height`, `warnings`. Полезное:

- `needs_transcription`: истина для всего, кроме текста.
- `input_path`: путь в виртуальной файловой системе агента, `/input/task.pdf`, `/input/task.png`, `/input/task.jpg`, `/input/task.webp` или `/input/task.txt`. Имя фиксированное ASCII (оригинал может быть кириллическим или с пробелами), расширение берётся от определённого типа: deepagents выводит MIME блока из пути.
- `to_file_data()`: `FileData` для deepagents (base64 для бинарного файла). Хостовая сторона кладёт его в состояние агента по `input_path` (`_task_message` в `hitl.py`).
- `content_blocks()`: блоки сообщения в стандартном формате langchain (`file` с `application/pdf` либо `image`). Формат закреплён тестом `tests/test_models_request_shape.py`.
- `metadata()`: JSON без содержимого файла (тип, размер, `sha256`, `input_path`, страницы, размеры, предупреждения). Именно это уходит в `run.json` как источник задачи.
- `describe()`: одна строка для логов, CLI и карточек.

В `intake/files.py` есть побочный эффект: для `.webp` регистрируется MIME в `mimetypes`, потому что на Windows с Python 3.12 его иногда не знают, и WebP ушёл бы как `application/octet-stream`.

## Роль intake

Источники: `roles.py`, `prompts/intake.md`, `config.py`.

- Роль объявлена в `roles.py` с `tool_groups=()` и `skills=False`: ни oracle-инструментов, ни навыков, только встроенное чтение файла (`read_file`).
- Модель роли задаётся в `config.py` (`MODELS["intake"]`, комментарий: переписывает PDF или картинку, нужно зрение; `EFFORT["intake"]` = `medium`). Модели ролей можно переопределить в `settings.json`, раздел `models.roles` (ключ `intake`).
- Роль вызывается только если задача пришла файлом. Главный агент не читает файл сам: инструкция в первом сообщении требует делегировать переписывание через `task` с `subagent_type "intake"`.
- Если в файле несколько задач, главному агенту сказано формализовать первую и сообщить об этом; выбор остаётся за человеком на HITL 1.

Что требует промпт (`prompts/intake.md`):

- Роль копировщик: не решает, не классифицирует язык, не даёт подсказок.
- Формулировка условия остаётся на языке оригинала, без сокращений и перестановок; формулы записываются нормализованным Unicode, не LaTeX (`aⁿbⁿ`, `{aⁿbᵐ | n ≥ m ≥ 0}`, `ε`, `∅`, `wᴿ`; без юникодных индексов `^(…)` и `_`). Правила грамматик по одному на строку со стрелкой `→` и `|`, регистр нетерминалов как в источнике.
- Нарисованный автомат записывается списком состояний, начального и финальных, и всех переходов `q₀ —a→ q₁`.
- Нумерация и подпункты сохраняются. Опечатки источника не исправляются, а упоминаются среди неуверенных мест.
- При нескольких задачах переписывается каждая полностью, нумерованным списком, с номером и страницей из источника.
- Формат ответа ровно два раздела: `## Tasks` и `## Uncertain readings`. Под вторым `- none`, если всё читалось ясно; если задачи нет вовсе или файл нечитаем, это сказано одной строкой в `## Tasks`, причина в `## Uncertain readings`.

> [!note] Что значит «неуверенное чтение»
> Каждое сомнительное место (смазанный или рукописный символ, обрезанный край, похожие символы `l`/`1`/`|`, `0`/`O`, `ε`/`e`/`∈`, `n`/`η`, `≤`/`<`) должно быть в списке: где оно, какие чтения возможны, какое поставлено в текст. Молча угадывать запрещено. Менять эти правила нужно в `prompts/intake.md`; код формат ответа не разбирает, текст ответа роли идёт человеку как есть.

## Как человек проверяет расшифровку (HITL 1)

Источник: `hitl.py`.

- Расшифровка показывается на остановке HITL 1 «formalization» вместе с IR, перефразировкой IR и словами из oracle. Эта остановка срабатывает после ответа ir-builder (или принятого вызова `validate_ir` главным агентом). Подробности остановки: [[hitl-and-review-modes]].
- `formalization_request` берёт расшифровку из последнего ответа субагента `intake` (`transcription`, не более 20000 символов). Если задача текстовая и `intake` не вызывался, поле `transcription` равно `None`, а карточка показывает «Task text» с текстом задачи.
- В карточке (`formalization_card`) для PDF и изображения сверху строка источника: тип, имя, число страниц, путь `stored_as`.
- Решения: `approve`, `edit`, `reject` с комментарием.
  - `edit` может менять поля `transcription`, `ir`, `class` (`FORMALIZATION_EDIT_FIELDS`). Пустая расшифровка при правке это `DecisionError`. Правка, совпадающая с оригиналом, не считается правкой.
  - При правке расшифровки модель получает сообщение «The task text, as corrected by the human» с исправленным текстом, и от неё требуется использовать именно его. Старые результаты oracle для прежнего IR не засчитываются для нового (подробно в [[verdict-gate]]).
  - При `reject` модель получает комментарий и команду заново вызвать `intake` и/или `ir-builder`; доказательство до нового одобрения не начинается.
- В CLI та же правка делается через `--decision edit --payload '{"transcription": "...", "ir": {...}}'`.

Исправленный текст важен и для отчёта: `_task_text` берёт условие для отчёта в таком порядке: расшифровка из последнего просмотра HITL 1, затем заданный текст задачи, затем ответ `intake`, иначе заглушка «(file …; no transcription)». Подробнее: [[reports]].

> [!warning] Режимы просмотра и авто-одобрение
> Режимы `all`, `formalization`, `auto` описаны в `hitl.py` (`auto_approves`). HITL 1 в режиме `formalization` никогда не одобряется автоматически, в режиме `auto` одобряется автоматически, то есть расшифровку PDF/картинки тогда никто не проверяет. Выключить точку HITL 1 в настройках или решать про авто-одобрение платного прогона решает пользователь, см. [[hitl-and-review-modes]].

## Где что хранится

- Исходный файл копируется в `RUN_DIR/input/task.<ext>` (`_store_input` в `hitl.py`); в `run.json` в записи источника лежит `metadata()` плюс `stored_as`. Для текстового входа файл не сохраняется, источник равен `None`.
- Файл передаётся агенту как `files={input_path: to_file_data()}` в состоянии запуска, а не путём в промпте. Как возобновляется запуск: [[run-lifecycle]].

## Что отлаживать и где

| Симптом | Куда смотреть |
|---|---|
| Файл отвергнут до запуска | сообщение с `code` в скобках; логика в `intake/files.py` |
| Предупреждение про расширение | `TaskInput.warnings`; ничего не сломано |
| PDF «слишком длинный» | `intake.max_pdf_pages` в `settings.json` или лимит API 100 |
| Картинка отклонена | 5 MB или 8000 px, лимиты API не поднять |
| Расшифровка в неверном формате | `prompts/intake.md`, раздел «Answer format» |
| Расшифровка не видна в карточке | `formalization_request` ищет ответ субагента `intake` в сообщениях; если главный агент прочитал файл сам, поля `transcription` не будет |
| Роль переписывает не тот язык или формулы | `prompts/intake.md`; модель и effort роли: `config.py` и `settings.json` |

Тесты на моках: [[testing-and-mock]]. Бюджет вызова роли `intake` как любого вызова модели ограничен проверкой перед запросом, см. [[budget]].
