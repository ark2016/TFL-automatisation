# Lean в deep-агенте

Путь формализации в Lean 4: код генерирует формулировку теоремы, модель пишет только тело доказательства, код собирает файл и проверяет его в Docker. Связанные заметки: [[tools-and-evidence]], [[verdict-gate]], [[roles-and-subagents]], [[budget]], [[reports]], [[testing-and-mock]].

> [!warning] Этот шаг необязателен
> В этом коммите ничто не заставляет агента идти в Lean. В плане работы в `prompts/main.md` нет шага «формализовать в Lean»: `lean-formalizer` упомянут только как одна из ролей, а `lean_check` в `prompts/main.md` назван опорным основанием для вердикта, если агент его вызвал. Ни `verdict_gate`, ни HITL не требуют `lean_check`. Вердикт без Lean законен. Вызывает ли агент Lean, решает он сам.

Теория, на которую опираются формулировки, здесь не пересказывается: см. `docs/THEORY.md`. Правило верификации Lean (R-Lean) задано в `docs/VERDICT_POLICY.md`; менять политику нужно там.

## Из чего состоит путь

Источники: `tfl_deep_agent/tools/lean.py`, `tfl_deep_agent/prompts/lean.md`, `tfl_deep_agent/roles.py`.

1. `lean_statement(ir, direction)` генерирует формулировку кодом, из IR.
2. Роль `lean-formalizer` пишет только тело доказательства (тактический блок, который встаёт на место `<PROOF>`).
3. `lean_check(statement_id, proof_body)` проверяет тело охранным сканером, собирает файл и компилирует его в Docker-образе `tfl-lean4`.

Группа инструментов называется `lean` (`group="lean"`). Эти два инструмента входят в набор главного агента и в набор роли `lean-formalizer`; у роли группы `lean` и `theory` (`roles.py`). Модель роли берётся из `config.py` (ключ `lean`), потолок `max_tokens` для роли `lean` равен 128000 (`MAX_TOKENS_PER_ROLE`), лимит одной компиляции `LEAN_TIMEOUT` равен 180 секундам. Деньги за вызовы модели считает [[budget]]; сама компиляция локальная и API не тратит.

## `lean_statement`

Источник: `tfl_deep_agent/tools/lean.py`.

- Направления: `regular` / `non_regular` (REG), `cfl` / `non_cfl` (CFL), `dcfl` / `non_dcfl` (DCFL). Тип `Direction` принимает ещё и `ll`.
- Формулировка рендерится теми же функциями, что и формализация в самих пайплайнах: `render_statement_verbose` из `agent_system.lib.lean_ir`, `cfl_system.lib.lean_ir`, `dcfl_system.lib.lean_ir` (какой модуль, зависит от направления; таблица `_DIRECTION_INFO`). Своего рендерера у deep-агента нет, формулировку не пишет модель.
- Ответ содержит: `statement_id`, `statement` (импорты, алфавит, определение языка, `theorem tfl_main : ...` без `:= by`), `template` (файл с маркером `<PROOF>`), `proof_body_rules`, `cls`, `side`, `claim`, `ir_fingerprint`, `max_checks`, `checks_used`.
- `statement_id` имеет вид `lean-` и 16 hex-символов: хеш текста формулировки и направления. Один и тот же IR и направление дают один и тот же id в любом процессе. Два IR, различающиеся только вне языка (например `source_text`), дают одну формулировку.
- Доверие результата всегда `not_verified`, `evidence_role = "reference"`: сама формулировка ничего не проверяет про язык.

> [!note] Нельзя подсунуть свою формулировку
> `lean_check` принимает только `statement_id`, но не текст формулировки. Формулировка живёт в кэше процесса (128 записей), модель её отправить не может. Если id неизвестен (например, после `--resume`), `lean_check` принимает необязательные `ir` и `direction`, заново рендерит формулировку и требует тот же id; иначе `ToolInputError`.

## Роль `lean-formalizer`

Источник: `tfl_deep_agent/prompts/lean.md`, `tfl_deep_agent/roles.py`.

Промпт фиксирует порядок: вызвать `lean_statement`, прочитать `statement`, `template`, `proof_body_rules`, написать тело, вызвать `lean_check`, исправлять по ошибкам. Если формулировка кажется неверной или недоказуемой, роль обязана это сказать, а не доказывать более лёгкое утверждение. В ответе роль возвращает `statement_id`, направление, итоговое тело, статус последней проверки с аксиомами и trust ровно как их выдал инструмент.

Каталог `skills/lean/` пуст; справка по API Lean (имена лемм из образа) лежит прямо в `prompts/lean.md`. Если менять версии Lean или Mathlib в образе, этот раздел промпта нужно сверить с образом, а не по памяти.

Различие между «роль вернула текст» и «проверка прошла»: ссылаться нужно на id записи `lean_check` в журнале доказательств, а не на ответ роли (`prompts/main.md`).

## Правила тела доказательства

Источник: `tools/lean.py` (`PROOF_BODY_RULES`, `guard_proof_body`).

Охранник работает до компиляции. Он вызывает `type_check.scan_proof_body` и добавляет свои проверки. Отклоняются:

- `sorry`, `admit`, `sorryAx`, `ofReduceBool`, `native_decide` (последнее по докстрингу `guard_proof_body`, проверка делегирована `scan_proof_body`);
- слово `axiom` в любом месте кода (шаблон `\baxiom\b` без привязки к строке);
- другое объявление (`theorem`, `lemma`, `def`, `instance`, `import` и т. д.) в начале строки (отдельный шаблон с привязкой к началу строки);
- ссылка на `tfl_main`;
- метапрограммирование и `#`-команды (это проверяет `type_check.scan_proof_body`; точный список его шаблонов здесь не приводится, смотрите сам модуль);
- ведущее `by`, символ табуляции, пустое тело, тело длиннее 40000 символов, строка в колонке 0.

Комментарии при проверке игнорируются. Отклонённое охранником тело даёт `status = "rejected"`, список `violations` и `proof_body_rules`; ничего не компилировалось, попытка не расходуется (счётчик увеличивается уже после охранника). Полей `attempt`, `attempts_left`, `errors`, `lean_file_sha256` в таком результате нет.

## `lean_check`

Источник: `tools/lean.py`. Сборку и компиляцию выполняет модуль `type_check` из `agent_system/lib/`; его код в этой заметке не разбирается, о нём известно только то, как его вызывает `tools/lean.py`.

Шаги: найти формулировку по id, прогнать охранника, проверить лимит попыток, собрать файл через `type_check.compose_lean_file` (по докстрингу `tools/lean.py`: формулировка, тело, независимый повтор ядром, `#print axioms tfl_main`), скомпилировать в Docker (`type_check.check_lean_file`, образ `tfl-lean4`). Сборка образа описана в корневом `README.md`.

Лимиты и поведение:

| Параметр | Значение | Что происходит |
| --- | --- | --- |
| `MAX_CHECKS_PER_STATEMENT` | 6 | Седьмая попытка в том же прогоне: `ToolBusy`, статус `attempt_limit` |
| `MAX_PARALLEL_CHECKS` | 2 | Параллельных компиляций не больше двух, иначе `ToolBusy` и попытка возвращается |
| `TOOL_TIMEOUT_S` | 600 | Общий срок инструмента |
| `DAEMON_RETRIES` | 2 | Повтор, если `docker run` упал до старта Lean (сообщения демона вроде `OCI runtime`) |

Счётчик попыток ведётся по прогону, а не по процессу: ключ `thread_id` из конфигурации LangGraph (или блок `lean_run(key)`; вне обоих случаев общий ключ `process`). Два прогона в одном процессе (TFL Lab, пакет `tfl-eval`) попыток не делят. Если Docker или образ недоступны, статус `unavailable`, попытка возвращается, результат это ошибка (`kind="unsupported"`), а не свидетельство.

Статусы, которые выдаёт инструмент: `proved`, `has_sorry`, `error`, `timeout`, `rejected`, `attempt_limit`, `unavailable`. Поля `attempt`, `attempts_left`, `errors`, `lean_file_sha256`, `axioms`, `n_errors` есть только у результатов, дошедших до компиляции (включая `unavailable`). У `rejected` от охранника и у `attempt_limit` их нет: там только общие поля (`statement_id`, `ir_fingerprint`, `proof_body` и т. п.), а у `rejected` ещё `violations`. Если тело отверг уже `compose_lean_file`, попытка при этом засчитана (счётчик увеличен до сборки), а результат несёт `status = "rejected"` лишь с общими полями. Длина списка `errors` и обрезка сообщений задаются функцией `_trim_messages` в `tools/lean.py`; точные числа сверяйте по ней.

> [!note] Номера строк в ошибках
> В собранном файле над `template` две лишние строки импорта (`Lean.Replay`, `Lean.Elab.Command`), поэтому строка N в сообщении соответствует строке N - 2 шаблона (`prompts/lean.md`).

## Что даёт `proved`

Источник: `tools/lean.py`, `agent.py` (функция, сопоставляющая запись журнала со стороной вердикта), `docs/VERDICT_POLICY.md` (R-Lean).

- Trust `verified` выставляется кодом, а не моделью, и только если статус `proved`, а список аксиом входит в `type_check.ALLOWED_AXIOMS` (`propext`, `Classical.choice`, `Quot.sound`). Подмножество аксиом проверяется ещё раз в самом инструменте, а также то, что `theorem tfl_main` объявлена в файле ровно один раз.
- `has_sorry`, `error`, `timeout` дают `not_verified`: это не свидетельство ни за, ни против (R1).
- В [[verdict-gate]] запись `lean_check` считается основанием для стороны вердикта, если одновременно: класс задачи один из `reg`, `cfl`, `dcfl` и совпадает с `data.cls`; `status == "proved"`; `trust == "verified"`; `side` равна `constructive` или `destructive`. Тогда сторона получает уровень `verified`. Результат читается как «язык этого IR принадлежит классу / не принадлежит», а привязка к IR идёт по `ir_fingerprint` (источник отпечатка виден в `data.ir_fingerprint_source`: `call`, `run` или `cache`). Правило привязки реализовано в `verdict_gate`; в этой заметке оно не разобрано, смотрите [[verdict-gate]].
- Из `prompts/main.md`: доказанный `lean_check` для `non_dcfl` при вопросе о LL(k) о языке остаётся лишь вспомогательным шагом, вердикт «не LL» публикуется как `uncertain` с confidence не выше 0.40.

> [!warning] Доказано то, что сгенерировано по IR
> `proved` относится к формулировке, построенной из переданного IR. Если IR неверно формализует задачу, результат остаётся верным для этого IR. Поэтому отпечаток IR должен совпадать с утверждённым на HITL 1 (см. [[hitl-and-review-modes]]).

## Кнопка Lean после отчёта

Источники: `tfl_deep_agent/followup.py` (`LEAN_REQUEST`, `PRESET_MESSAGES`, `lean_refusal`, `_proved_in`), `ui_server/deep_routes.py` (`api_message`, `_lean_view`), `ui_server/static/deep.js` (`deepLeanAction`).

Кроме решения самого агента, человек может запросить Lean после принятого отчёта. В TFL Lab под последней итоговой карточкой стоит кнопка «Формально верифицировать (Lean)». Она отправляет сообщение-заготовку `POST /api/deep/runs/<id>/message {"preset": "lean"}`: текст `LEAN_REQUEST` просит поручить доказательство роли `lean-formalizer`; если `lean_check` вернёт `proved`, заново отправить полный отчёт через `submit_report` со ссылкой на id этой записи; иначе прямо сказать, на чём доказательство остановилось, а ответ и отчёт оставить без изменений. Это обычное сообщение-продолжение ([[run-lifecycle]]), поэтому новый отчёт проходит HITL 2 по режиму запуска, а кнопки в CLI нет (то же сообщение можно отправить через `--message`).

Кнопка скрыта (`followup.lean_refusal`, в ответе деталей запуска `followup.lean`):
- нет принятого отчёта (`status` не `submitted`);
- класс отчёта `ll` (Lean-пути нет);
- отчёт уже ссылается на `lean_check`, который шлюз засчитал бы: `_proved_in` требует, чтобы `result["trust"] == "verified"` и чтобы процитированная запись журнала с результатом давала сторону вердикта по `lean_proof_side`, то есть предикату шлюза с правилом отпечатка IR ([[verdict-gate]]). Просто `verified` от других инструментов кнопку не прячет;
- общие причины закрытого продолжения (запуск работает, ждёт решения, отменён, прерван).

Для live-запуска кнопка требует второго нажатия (встроенное подтверждение расходов) и показывает модель роли `lean` и `per_subagent_max_usd`; сервер требует `confirm_spend`. Это вызов модели: он идёт по общему правилу о живых запусках ([[budget]]). Что сообщение значит для вердикта, решает шлюз по записи `lean_check`, а не текст сообщения.

## LL(k) без Lean

Источник: `tools/lean.py`, `prompts/lean.md`, `prompts/main.md`, `README.md`.

`lean_statement` на `direction="ll"` бросает `ToolUnsupported("LL(k) is not formalized in Lean: ...")` (причина берётся из рендерера `agent_system.lib.lean_ir`). Для LL(k) верификация идёт через `ll_table` и родственные инструменты, а не через Lean. В `prompts/main.md` при выборе класса отмечено, что у REG, DCFL и CFL есть `lean_statement`, а у LL(k) нет.

## Отчёт

Источник: `tfl_deep_agent/reports/render.py`, `tfl_deep_agent/evidence/policy.py`.

- Шаблон `lean_appendix` добавляет к `full_proof` раздел Lean (статус, аксиомы, формулировка, тело, файл доказательства). Раздел добавляется и к любому другому шаблону, если в отчёте есть блок `lean` или в журнале есть результат `lean_check`.
- Статус раздела берётся из записей `lean_check` журнала; если записи нет, пишется «не подтверждён журналом», trust `not_verified`.
- Идентификаторы из `lean.evidence_ids` отчёта проходят ту же проверку на существование в журнале, что и остальные цитаты (`evidence/policy.py`). Подробнее: [[reports]].

## Как отлаживать

- Нужен только текст формулировки: вызвать `lean_statement` в мок-сценарии, проверить `statement_id` и `template`. Для проверки без Docker тесты подменяют `_run_lean` (комментарий в `tools/lean.py`); сам Docker-путь в тестах пропускается с причиной, если Docker недоступен (`README.md`, см. [[testing-and-mock]]).
- Модель «застряла»: в результатах `lean_check`, дошедших до компиляции, смотреть `attempts_left`, `errors` (с поправкой на две строки в номерах) и `lean_file_sha256`; у `rejected` смотреть `violations`, у `attempt_limit` лимит уже исчерпан.
- `unavailable`: проверить демон Docker и наличие образа `tfl-lean4`. Попытка в этом случае не списывается.
- Живые вызовы модели для написания доказательства идут по общему правилу: только по явной просьбе и с согласованным бюджетом (`CLAUDE.md`, [[budget]]); по умолчанию работает мок-режим.
