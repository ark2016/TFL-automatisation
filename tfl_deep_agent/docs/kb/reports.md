# Слой отчёта (submit_report, шаблоны, рендерер, диаграммы)

Модель отдаёт структурированные поля через `submit_report`. Код проверяет их, подставляет в шаблон и сам дописывает всё, что касается доверия: метки, потолок уверенности, приложение «Проверка», объекты из результатов инструментов, диаграммы. На выходе `result.json`, `result.md` и `result.html`.

Связанные заметки: [[verdict-gate]] (откуда берутся `trust` и `confidence_cap`), [[tools-and-evidence]] (журнал доказательств и id вызовов), [[hitl-and-review-modes]] (HITL 2 и пометка об отсутствии проверки человеком), [[lean]] (раздел Lean в отчёте), [[tfl-lab]] (показ отчёта в интерфейсе), [[index]].

## submit_report: поля и проверка

Источник: `tfl_deep_agent/tools/report.py`.

`SubmitReportArgs` наследует `ToolArgs` (`extra="forbid"`). Полей `trust`, `confidence`, `verified` в схеме нет, так что модель не может задать доверие. Обязательны `verdict`, `language_class` (`reg` / `cfl` / `dcfl` / `ll`), `method` и `steps` (от 1 до 60 шагов). Остальное необязательно: `answer` (`yes` / `no` / `inconclusive`), `hypothesis`, `lemmas`, `claims`, `construction`, `conclusion`, `summary`, `evidence_ids`, `ir_fingerprint`, `template`, `lean`.

Вложенные модели: `ReportStep` (`title`, `claim`, `justification`, `theorem_ids`, `evidence_ids`), `ReportClaim` (`text`, `evidence_ids`), `ReportLemma` (`theorem_id`, `use`), `ReportLean` (`evidence_ids`, `proof_path`, `note`). У каждого текстового поля есть предел длины.

Проверки идут по порядку внутри одного вызова:

1. **Схема.** Ошибка pydantic превращается в JSON `error_kind: "invalid_input"` с текстом (до 1500 символов). Отчёт не записывается, модель получает ещё ход.
2. **Идентификаторы теорем.** Валидатор модели сверяет `lemmas[].theorem_id` и `steps[].theorem_ids` с `docs/THEORY.md` через `tools/theory.py` (`load_theory`). Неизвестный id отклоняется как `invalid_input`: это часть проверки схемы, а не отдельный вид ошибки. Если файла теории нет (нет checkout), проверка пропускается, а рендерер помечает id, которые не смог разрешить.
3. **Разметка вызова внутри полей.** `leaked_markup_fields` ищет в любом строковом поле `<parameter`, `<invoke`, `<function_calls` (с префиксом `antml:` или без) и закрывающие теги вида `</hypothesis>`, `</steps>`. Так выглядит сломанный вызов, где одно поле «проглотило» следующее. Отчёт отклоняется, текст ошибки называет поля и просит подать заново.
4. **Идентификаторы доказательств.** Только если у инструмента есть журнал: его передают в `make_submit_report_tool(evidence=...)`, иначе берётся журнал окружающего блока `use_evidence`. `cited_evidence_ids` (определена в `evidence/ledger.py`, `tools/report.py` её импортирует) собирает id из `evidence_ids`, `claims[].evidence_ids`, `steps[].evidence_ids` и `lean.evidence_ids`; `unknown_evidence_ids` находит те, которых нет в журнале. Один неизвестный id отклоняет весь отчёт. Без журнала id здесь не проверяются.

> [!warning] Что значит отказ
> Отказ по пунктам 3 и 4 возвращается как `ToolException`: ToolMessage без артефакта. Поэтому отчёт не фиксируется, а шлюз отчёта в `agent.py` его не видит. HITL 2 срабатывает раньше инструмента и решает отдельно (`when` в `hitl.report_interrupt_config`): не останавливается на отчёте, не прошедшем схему, и на неизвестных id, если конфигурации передан журнал. Разметку вызова (пункт 3) он не проверяет, поэтому человек увидит такой черновик, а отказ придёт после одобрения. Успешный вызов возвращает артефакт `{"tool": "submit_report", "ok": true, "report": {...}}`; именно его читает `agent._is_submitted_report`.

Сообщение о неизвестных id (`evidence_id_error`) содержит: сами id и место цитирования, пометку «a tool NAME, not a call id», если модель указала имя инструмента, и допустимые id, сгруппированные по имени инструмента, с уровнем доверия, отпечатком IR и ролью (кроме `main`). В список попадают только успешные результаты, не больше `MAX_LISTED_IDS` (60, остаются новейшие). Код никогда не подставляет id вместо имени инструмента: модель подаёт отчёт заново сама.

Второй рубеж: рендерер и шлюз вердикта понижают доверие для id без записи в журнале (отчёт без журнала, повторная оценка вне запуска). Подробнее: [[verdict-gate]].

`validate_report(fields)` проверяет те же поля вне инструмента и возвращает JSON-дамп. По докстрингу модуля он нужен для правок человека на HITL 2. Ошибка здесь `pydantic.ValidationError`.

## Шаблоны

Источник: `tfl_deep_agent/skills/report-templates/`, `TEMPLATE_INFO` в `reports/render.py`.

Модель выбирает один из `SELECTABLE_TEMPLATES`: `full_proof` (по умолчанию), `exam_solution`, `short_verdict`, `lean_appendix`. Файлы `*.md` — это `string.Template` с плейсхолдерами `$verdict_block`, `$steps` и т. п.; полный набор допустимых имён лежит в `PLACEHOLDERS`. Шаблон меняют в `.md`; если меняется состав полей или назначение, синхронно правят `TEMPLATE_INFO` и `SKILL.md` (его читает модель, а `list_report_templates` берёт названия и описания из `TEMPLATE_INFO`).

- `full_proof`: условие, ответ, идея, леммы, конструкция, ключевые утверждения, шаги, заключение.
- `exam_solution` и `short_verdict`: компактные, шаги идут в плейсхолдер `key_steps`; у `short_verdict` вместо идеи стоит `summary`.
- `lean_appendix`: тело берётся от `full_proof`, а сам файл `lean_appendix.md` — это раздел Lean. Этот раздел добавляется к любому шаблону, если есть блок `lean` в отчёте или в журнале есть результат `lean_check` (`_wants_lean`). Подробности: [[lean]].
- `partial`: внутренний шаблон, модель его выбрать не может (`render_report` на неизвестное имя бросает `ValueError`). Используется, когда принятого отчёта нет (`budget_exhausted`, `incomplete`, `error`): «Ответ не установлен», доверие `not_verified`, установленное и опровергнутое берутся из журнала.

`list_report_templates` — обычный инструмент реестра (группа `report`, доверие всегда `not_verified`): без `name` перечисляет четыре шаблона, с `name` добавляет текст и плейсхолдеры.

## Рендерер: что делает код, что приходит от модели

Источник: `tfl_deep_agent/reports/render.py`.

`render_report(result, evidence=, budget=, ...)` читает результат `agent.collect_result`, журнал доказательств (путь к `evidence.jsonl`, список записей или объект журнала) и журнал бюджета. `write_report(run_dir, result)` пишет три файла и сам подхватывает `run_dir/evidence.jsonl`.

От модели в текст попадают: `verdict`, `method`, `hypothesis`, `construction`, `conclusion`, `summary`, формулировки и обоснования шагов и утверждений, поле `use` у лемм. Всё это проходит через `safe_text`: строки, начинающиеся с `#`, `>` или тройного обратного апострофа, экранируются, так что модельный текст не откроет заголовок, цитату или блок кода. Исключение — `construction`: её обрабатывает `safe_block`, где блок кода остаётся блоком (рендерер сам закрывает незакрытый), а текст вне блока экранируется.

Код генерирует сам:
- уровень доверия и потолок уверенности («Уверенность: N%» — это потолок, заданный кодом); рендерер доверие не повышает и берёт `result["trust"]` из шлюза вердикта. Только если доверия в результате нет, он вызывает `agent.verdict_gate` сам;
- предупреждающую плашку в блоке «Ответ», если проверка неполная, и строку о ревью человеком; запуск без одобрения человека помечен `NO_HUMAN_REVIEW_MARK` («без проверки человеком»), правки человека перечислены;
- пометки у шагов и утверждений вида «(проверено: regex_to_dfa ✓)» (только когда доверие самого шага не ниже `well_formed`). Префикс `MARK` — невидимый символ, `safe_text` вырезает его из модельного текста, чтобы модель не подделала пометку;
- цитаты теории: название раздела и диапазон строк `docs/THEORY.md` по id раздела;
- объекты из результатов процитированных вызовов: таблицу переходов ДКА, грамматику, таблицу LL, диаграммы (раздел «Конструкция»);
- статус и аксиомы Lean: читаются из записей `lean_check`, а не из текста модели;
- приложение «Проверка» (`EVIDENCE_BLOCK_TITLE`): таблица вызовов, основание ответа, замечания шлюза, строки IR и ревью, запуск, модели и стоимость. Оно дописывается после шаблона, поэтому ни один шаблон не может его убрать. В HTML оно лежит в отдельной секции `data-generated-by="code"`.

`result.json` содержит исходный результат и блок `rendered` (шаблон, вердикт с доверием, утверждения, шаги, леммы, использование id, целостность журнала, бюджет). Поля `data` и `args` записей журнала в `rendered.evidence` не дублируются.

HTML строит собственный `markdown_to_html` (поднабор Markdown, всё экранируется, формулы `$...$` оставляются для KaTeX; KaTeX подключается, только если в тексте есть формулы).

## Версии отчёта при сообщениях

Источники: `tfl_deep_agent/followup.py`, `hitl._finish_segment`, `reports/render.py` (`normalize_budget`, `_evidence_block`).

Завершённый запуск принимает сообщения ([[run-lifecycle]]), и отчёт может меняться:

- Перед каждым сообщением `result.{json,md,html}` копируется в `report_history/<n>/`. Сообщение, которое не закончилось, возвращает последнюю копию (`restore_report`).
- `run.json` `report_revision` считает версии отчёта как объекта, а не файлов. Текстовый ответ перерисовывает `result.*` (меняется раздел о бюджете), но версию оставляет; новая версия появляется, когда изменились статус, вердикт, доверие, потолок уверенности или `report_digest` (хеш объекта отчёта). Для версий со второй URL отчёта в TFL Lab получают `?v=<версия>`.
- Если на остановке по бюджету человек добавил денег, приложение «Проверка» дописывает строку «Бюджет добавлен» с суммой, новым лимитом, решившим и временем (`budget["extensions"]`).
- «Условие» отчёта всегда исходная задача (текст, расшифровка файла или текст, исправленный человеком на HITL 1). Сообщение чата, которое привело к новому просмотру IR, хранится в просмотре как `followup_text`, показывается на карточке HITL 1 и печатается в отчёте отдельным блоком «Уточнение» (`result["clarifications"]`, все по порядку; плейсхолдер `clarification_section`). Звёздочки условия вне `$...$` / `$$...$$` экранируются (`safe_task_text`), поэтому `(ab)*` не превращается в курсив; математика остаётся KaTeX.
- Просмотр принятого отчёта в другом шаблоне (`POST .../render`, TFL Lab) пишет в `views/<шаблон>.{md,html}` и `result.*` не трогает: [[tfl-lab]].

## Диаграммы состояний

Источник: `tfl_deep_agent/reports/diagrams.py`; вызовы из `_ledger_objects` в `reports/render.py`.

- `dfa_to_dot(dfa)`: DOT для ДКА `{states, alphabet, start, accept, transitions}`. Параллельные дуги сливаются в одну с подписью `a, b`, принимающие состояния рисуются двойным кругом, «ловушка» (непринимающее состояние, где все буквы ведут в него же) пунктиром.
- `dpda_to_dot(dpda)`: DOT для ДМП-автомата в формате dcfl (`transitions: [{from, read, top, to, push}]`); подпись дуги `a, Z / AZ`, пустое чтение и пустая запись показываются как `ε`.
- `dot_to_svg(dot)`: запускает `dot -Tsvg`, возвращает встраиваемый SVG, где `stroke="black"`, `fill="black"` и `fill="white"` заменены на `currentColor` / `none`, чтобы картинка читалась на светлой и тёмной странице.

Диаграмма строится только для объектов из процитированных вызовов (основание вердикта, `evidence_ids`, шаги, утверждения; `lean.evidence_ids` сюда не входят): ДКА из `regex_to_dfa`, `dfa_vs_ir`, `run_dfa`, `nerode_probe`; ДМП-автомат из аргументов `dpda_vs_ir`, `dpda_run`. Для каждого вида берётся один объект.

**Пределы.** `MAX_DIAGRAM_STATES = 30`, `MAX_DIAGRAM_EDGES = 120`, `DOT_TIMEOUT_S = 15`. Если автомат больше или у ДКА нет переходов, `*_to_dot` возвращает `None`, и диаграммы нет (таблица переходов остаётся).

**Рисуется только DOT, созданный кодом.** `_Ctx.diagram` кладёт исходник DOT в словарь `ctx.diagrams` (исходник → SVG) и пишет в Markdown блок с тегом `dot`. `markdown_to_html` превращает такой блок в `<figure class="diagram">` только если его текст является ключом этого словаря. Блок `dot` в модельном тексте (например, в `construction`) остаётся обычным кодом. Причина названа в докстринге: HTML-метки Graphviz умеют читать локальные файлы через `<IMG SRC>`. Дополнительно: `_q` экранирует `\` и `"` и убирает переводы строк, чтобы идентификатор не мог закрыть строку; `dot_to_svg` отбрасывает результат, в котором есть `script`, `foreignObject`, `iframe`, `image`, `use`, атрибуты `on...=` или `javascript:`.

> [!note] Без бинарника dot
> `dot_binary()` ищет `dot` в `PATH` один раз за процесс. Если его нет, а также при ошибке запуска, ненулевом коде возврата или тайм-ауте, `dot_to_svg` возвращает `None`, и в `ctx.diagrams` записывается пустая строка. Ничего не падает: в HTML исходник DOT остаётся блоком кода рядом с таблицей переходов, а в `result.md` блок `dot` присутствует всегда.
